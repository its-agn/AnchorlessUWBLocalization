# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

**Anchorless UWB Localization** — Senior Design project, Team A01. A system that tracks
several mobile nodes *relative to each other* in GPS-denied (indoor) spaces using
peer-to-peer UWB time-of-flight ranging, with **no fixed anchor nodes**. An IMU (or other
secondary motion sensor) is fused with UWB to cover cases where ranges alone can't see
motion. A lightweight, traditional ML model (not deep learning) estimates how much to
trust each range so NLOS (non-line-of-sight) measurements get down-weighted.

Main use case: fleet robotics and anything else where position relative to the group or
a start point matters more than global position. The long-term goal is "plug and play"
localization, and a stretch goal is moving localization/ML off the central computer
onto the nodes.

Source documents (in the repo root, not tracked by git):
- `Design Proposal & Team Contract - A01.pdf` — motivations, technical outline, tech
  stack, two-semester timeline, roles.
- `UWB Ranging - Roles & Rough Timeline.pdf` — earlier, shorter version of the roles.

## System architecture (planned)

```
DWM3001C (UWB, C/C++ firmware) ──► Node computer (Pi Zero 2 or similar SBC) + IMU
        peer-to-peer DS-TWR              collect, preprocess, log locally
                                                │  2.4 GHz Wi-Fi (mostly one-way)
                                                ▼
                                 Central laptop/desktop
                    ingest + time sync → localization / sensor fusion (EKF)
                    → NLOS confidence weighting → backend → live map, logging, replay
```

- **UWB module:** Qorvo DWM3001C (DW3000 family), channels 5 (6.5 GHz) / 9 (8 GHz).
  Provides ToF plus RF diagnostics and CIR data for NLOS work.
- **Node compute:** Raspberry Pi Zero 2 or similar (not final; Teensy and ESP32 have
  also been discussed). IMU not final (MPU6050 is a candidate). Battery TBD.
- **Data goes over Wi-Fi, not UWB.** UWB is only for ranging.
- **Central computer** runs the main localization, sensor fusion, NLOS model, backend,
  logging and live visualization for the first version. Keep these pieces separable so
  they can later move onto the nodes.
- Languages: C/C++ for firmware; Python (possibly C++) on the central computer.
- Target is ~5 nodes, so each node has 4 ranges, which is enough for 3D multilateration.

## Synthetic data: what to know

Full details are in `Localization/test_cases/README.md`. Key points:

- 5 nodes `N1`–`N5` on a flat 10 × 10 m floor, all at z = 1.0 m (so the problem is 2D).
  Max pair separation 15 m. DS-TWR on channel 5. TDMA: 10 pairs × 10 ms slots = 100 ms
  cycle, so each pair is ranged at 10 Hz. The initiator alternates each cycle.
- `timestamp_us` is on a shared, already synchronized clock. `seq` is per source node
  and restarts at 0 after a reboot.
- `status` is `ok`, `timeout` or `rx_error`. For failed attempts, ToF, distance and
  `diag` are `null`.
- 1 DTU = 1/(128 × 499.2 MHz) ≈ 15.65 ps; `distance_m = tof_ps × c_air`, with
  c_air = 299,702,547 m/s.
- Non-ML NLOS signal: `rssi_dbm − fp_power_dbm` is < 6 dB for LOS and > 10 dB for NLOS.
- **Never feed `labels.jsonl` or `ground_truth.csv` into the system under test.** Use
  them only for scoring.

| Case | What it exercises |
|------|-------------------|
| TC01 | Static LOS baseline: noise floor, basic multilateration |
| TC02 | Long range near the 15 m limit: noise and timeouts that grow with distance |
| TC03 | One moving node, four static |
| TC04 | All nodes moving (random walks) |
| TC05 | Rigid group motion: ranges never change. UWB alone can't see this; it's the IMU case |
| TC06 | Parallel pair with static nodes present, so the motion is observable |
| TC07 | Near-collinear degenerate geometry (reflection ambiguity), then recovery |
| TC08 | NLOS: drywall, concrete pillar, walking person |
| TC09 | Packet loss, link outage, node reboot (seq reset) |
| TC10 | Corrupt, impossible, late, out-of-order and duplicate packets |

`scenario.json` and the README mention "MVP 1.d / 1.e / 3.f" requirements. That MVP list
isn't in this repo.

## Core technical problems (from the proposal)

When designing localization code, account for:
- **Unobservable motion:** parallel or rigid-group motion keeps all pairwise distances
  constant. Without anchors, UWB can't detect it (TC05). This is why the IMU and EKF exist.
- **Gauge freedom:** relative positions are only defined up to rotation, translation
  and reflection. Coordinate-frame and startup initialization still need to be decided.
- **Degenerate geometry:** collinear/coplanar layouts, too few valid ranges, poor GDOP.
  Detect these and report low confidence instead of returning a confident wrong answer.
- **Missing or invalid data:** dropped ranges, nodes going offline and recovering,
  seq resets, stale, duplicate or out-of-order packets, physically impossible ranges.
- **NLOS bias:** NLOS ranges read long, with higher variance. Build a non-ML baseline
  first (RSSI/first-path gap, other RF diagnostics), then try a Random Forest or another
  traditional model for per-range confidence and use it to weight measurements.

## Design principles for new code

- Keep **raw measurements, processed measurements and final position estimates
  clearly separated** so it's possible to tell where error comes in.
- Carry **confidence/uncertainty** with every node estimate and link. Don't output a
  bare point.
- Build **logging and replay** early: every test should be recordable and re-runnable
  offline, and the same recording should be replayable through different algorithm
  versions for comparison.
- Define **benchmarks against ground truth** (e.g. position RMSE after aligning frames)
  so "better" means a measured improvement, not a visual impression.
- Ingestion must handle data arriving at different times. Decide explicitly how far
  apart two measurements can be and still count as the same instant.
- Keep compute small enough that localization/ML could later run on node hardware.
